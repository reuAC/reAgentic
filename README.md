# reAgentic 第一版

## 概述

以主模型直接处理用户输入，并在多轮对话中使用上下文工程，该结构能够兼顾对复杂任务的处理与简单任务的快速回复。

整个框架以工具为驱动运行。

其中，工具分为特定智能体工具、自定智能体工具与普通工具。

1. 特定智能体工具：能够输入用户提示词作为参数，以运行大模型的工具，即调用该工具等同于调用一个大模型。
2. 自定智能体工具：能够输入系统提示词与用户提示词，以运行大模型的工具，即调用该工具等同于调用一个大模型。
3. 普通工具：通过输入参数后以一定逻辑处理后返回处理结果或处理状态的工具，没有调用大模型的功能。

主模型能够通过调用智能体工具将任务委派给下属智能体，智能体将任务完成结果返回，以减少主模型的token使用，保证主对话的纯净，提高稳定性。

智能体工具所指向的智能体中能够嵌套智能体工具，但不应使用回环，且应当有嵌套的最后一环。

智能体工具应当附加合适的提示词，引导主模型在调用是输入必要的提示词。

智能体工具互相独立，指定调用的大模型应当能够自定义，以用于切实调用擅长不同领域的大模型。

建议的结构为：主模型调用多个智能体工具分派任务，并处理返回信息进行下一步调用工具或最终回答。

## 框架

### 主模型

赋予主模型多个工具，包含智能体工具与普通工具

#### 智能体工具

1. 特定领域：负责特定领域的智能体，以不同型号模型为分割，使得主模型能够按照领域调用模型。
2. 特定操作：负责进行可复用操作的智能体，如网页部署、文件打包、内容上传、网页搜索等，使其专门处理相关内容。
3. 长上下文大模型：存在一个长上下文大模型，在使用时输入当前用户输入与全部上下文，令其总结所需的相关信息并返回。
4. 自定智能体：令主模型在遇到没有特定智能体处理的任务时，积极使用该工具创造自定智能体进行处理，并获取结果，而并非自行处理。在处理时可以新增一个输入参数用于指定模型的智能程度，由主模型决定。

#### 普通工具

普通工具种类繁多，应当根据需求在各个智能体下添加，其中，一步就可以完成任务的工具可以直接挂载在主模型下（如画图、写作）。

## 运行时

在运行是，用户将内容输入到主模型，主模型分析用户意图并按需调用工具以逐步完成。

## 上下文工程

本策划中让主模型以工具的形式调用智能体工具，随后智能体工具将该步骤的结果返回的方案旨在源头可控的减少上下文的内容，因为思考、处理仅在智能体工具内进行，同时若有相关的循环、嵌套的逻辑亦如此，仅有精简的处理结果与处理状态在主模型的对话序列中存在，这首先在源头上减少了需要处理的文本数量。与此同时，该方案在逻辑上也同时进行了为智能体工具选择上下文、为主模型压缩上下文、隔离上下文。

为了进一步提升协作与稳定性，本文提出在该框架下的所有智能体应当共同维护一个基于单个对话的知识库。

### 知识库

下文中，所有内容均意指存在于单个独立的对话中。

能够轻易发现，该方案下的智能体以工具为单位进行相关处理，主模型基于调用智能体工具来进行处理，由智能体工具处理信息并返回质朴的结果。

故，规定全部工具返回的内容，以知识为单位保存在知识库中，传递时以知识编号为占位符代指。

知识有如下属性：

1. 编号
2. 所属项目
3. 概述
4. 类型（如代码、图片、表格等）
5. 子库（如代码库，代码应当以文件为拆分存在于子库下，相关智能体应当按逻辑存储）
6. 与当前对话的距离（信息整合读取时显现）

根据规定，智能体工具间传递大文本信息时使用编号而非原文，其能够减少在传递过程中模型不受控的修改内容。

存在知识库工具，智能体能够通过输入以下任一内容获得对应内容：

- 编号
- 所属项目（获得项目下的项目树结构）
- 所属项目与子库名（获得对应子库下树结构）
- 类型（获得与当前对话距离最近的有添加或改动的对应类型的知识）

主模型接收请求皆为无状态的，即如下情况。

- 传统状态：[用户输入]\[模型回答][用户输入]\[模型回答][用户输入]\[模型回答]……
- 无状态：[上下文工程整合信息]\[用户输入][模型回答]

提示词中应当有模型能够使用[this]来代表当前的用户输入，用户输入以次序为编号存入知识库，当前会话下主模型调用工具时使用的占位符自动转译为编号。

当用户输入时，可选的并行出一个进程对用户输入进行分析并制作概述，附加到对应编号的知识中，流程如下。

1. 接收用户输入，其中前端应当能够将长复制信息、文件等单独分割。
2. 单独开辟线程，输入用户输入与概述生成提示词、单独分割出的内容，让模型生成对应简约标题、概述。
3. 将分割出的内容与对应标题、概述以知识为单位存储到userinput知识下。
4. 当信息整合时，应当显式的给出每次用户输入所附加的内容的标题、概述。

在处理用户输入，而调取智能体工具或工具时，应当附加一个项目名为参数，智能体工具在与知识库交互时，应将内容附加到项目下，以项目名为根，形成一个树状结构。

此时，当用户输入后，应当在整合信息中添加当前的知识库顶层状态。

（假设存在已经制作了三个web项目，其中一个通过深度搜索并制作调研结果的网页，另两个是根据要求进行的）

{

project:web1_research{code1/;image1{概述：阳光明媚的沙滩}}:3

project:web2{code1/;}:2

project:web3{code1/;}:1

userinput{1,2,3}

}



# reAgentic 第二版

## 概述

以主模型为策划者，以工具为驱动处理任务，令主模型仅关注任务的规划而非具体执行，从而实现全能智能体。

### 要素

- 智能工具：以调用另一个智能体为目标的工具，能够接收参数作为提示词或其他用途，并返回处理结果或处理状态。能够嵌套另一个智能工具。
- 普通工具：基于输入参数而处理任务的传统工具。

## 上下文

取消对上下文的记忆，在每次用户输入后构造提示词以触发单次对话，即无状态对话，称构造的提示词为整合信息。

### 协作

主模型、智能工具共同维护一个知识库，知识库针对于单次会话建立。

#### 知识库树

存在一个知识库树，其中该次对话所属的知识库的全部内容，示例如下。

在使用知识库树构建整合信息时，开发者使用变量占位符将指定内容注入到提示词中。

#### 知识

知识有如下属性：

1. ID编号
2. 所属项目
3. 概述
4. 类型（以文件后缀名为分类，其中子库具备特别的类型）

知识分为零散文件与项目子库，项目子库中的内容以标准的文件系统管理，智能工具可以经由上层授权访问与管理子库内容。

#### 处理逻辑

主模型在每次处理对话前，以整合信息作为提示词获得了目前的知识库树。

主模型作为主策划判断调用的智能工具并实施调用，调用时应附上作用于的项目名，允许附上多个项目或项目子库，此时该智能工具就具备了访问与管理该项目的权限。

#### 授权

权限具有传递特性，当智能工具下属仍有智能工具，则智能工具在需要调用其时也可以附加上项目名或子库名，此时对应工具则具备了对应知识的访问与管理权限。

未经上层授权的项目，智能工具无法访问，也因调用时的提示词构造无法”看到“其内容。

## 框架

任何处理流程均附有上述上下文机制，均不对上下文进行记忆，每次请求均不附加对于上文原文内容的记忆。

主模型、智能工具均被挂载知识库增、删、改、查工具，允许在权限范围内进行操作。

### 主模型

作为策划者，不得对任何任务做具体的处理，故此处仅允许挂载智能工具。

### 智能工具

根据上层指令结合所属工具处理任务，作用于上层指定的库或子库，允许嵌套另一个智能工具，以进一步分摊处理。

任务应当使用工具对目标库或子库进行操作，而非在工具返回处理结果或成果，当任务确认完成时，使用任务完成工具返回处理状态与操作的库或子库与内容增删情况。

#### 最佳实践

对智能工具做尽可能细致的划分，如编写代码的智能工具示例如下。

结构如下。

- 网页服务编写协调智能工具：下属前端智能工具、后端智能工具。
- 前端智能工具：接收需求，并编写对应内容。
- 后端智能工具：接收需求，并编写对应内容。



处理逻辑如下。

1. 网页服务编写协调智能工具：编写API开发文档与前后端通信方式，异步发送给下属智能工具，令前后端能够同时并发开发。
2. 前端智能工具、后端智能工具：接收需求，并编写对应内容。
3. 网页服务编写协调智能工具：接收到完成信号，操作虚拟机开始部署。
